# PRD — detect.expert (спецификационное имя: Detector)

Версия: 0.1 (эпик E01). Статус: черновик, согласован с ТЗ v2.0 (`Doc/Detector_Enterprise_Technical_Spec_RU.md`, контрольная дата источников 12.09.2026).
Владелец: TBD. Неизменяемые границы: `docs/PROJECT_RULES.md` (REQ-001…REQ-015). Связанные документы: `docs/glossary.md`, `docs/ui-copy.md`, `docs/data-inventory.md`, `docs/coverage/matrix.md`, `docs/decisions/ADR-001…016.md`, `docs/architecture/*`.

## 1. Назначение

Chrome-расширение Manifest V3, которое объясняет пользователю:

1. какие обращения к браузерным API и какие сетевые действия **наблюдались** на текущем документе;
2. какие сочетания наблюдений **похожи** на получение браузерного отпечатка (гипотеза, не вердикт);
3. какие **известные сервисы защиты и идентификации** могут быть связаны с наблюдаемыми ресурсами (совпадение с каталогом, не оценка доверия);
4. что осталось **вне области наблюдения** (coverage).

Продукт информационный. Он не защищает, не блокирует, не анонимизирует и не выносит вердикт о безопасности сайта (REQ-001, REQ-002, REQ-007, REQ-015).

## 3. Три режима одного продукта

| Режим | Для кого | Обработка | Управление | Сервер |
| --- | --- | --- | --- | --- |
| **Local** | Индивидуальный пользователь | Только текущие документы разрешённых сайтов; агрегаты в `storage.session` | Пользователь выбирает уровень доступа (ADR-003) и может приостановить наблюдение | Нет |
| **Managed local** | Организация | Та же локальная модель; ограничения через `chrome.storage.managed` (ADR-013) | Chrome managed policies; UI показывает, что задано организацией | Нет для анализа |
| **Managed connected** (опциональный этап, E18–E19) | Организация с потребностью в проверяемых отчётах и fleet-управлении | Локальный анализ плюс отдельно включённые минимальные сообщения (health, ручной отчёт, data-only rule pack) | Все источники управления и получатели отображаются пользователю | Отказ сервера не останавливает локальный анализ |

Срез 1 (внутренний отчёт) реализует только **Local**. Managed local и Managed connected описаны в ADR-013…ADR-015 со статусом Proposed.

Формулировка Local для Store: «Расширение не отправляет результаты анализа и не обращается к серверам разработчика». Не «браузер никогда не использует сеть»: обновления расширения выполняет Chrome Web Store.

## 4. Пользователи и критерии успеха

| Роль | Успех |
| --- | --- |
| Пользователь | За несколько секунд после открытия popup понимает: что наблюдалось, что из этого обычное использование API, что требует внимания, какие сервисы распознаны и что осталось вне наблюдения |
| Исследователь | Открывает конкретную находку и проверяет признаки (`signalCodes`), источник (`evidenceSource`/`integrity`), правило и его версию, ограничения и альтернативные объяснения |
| Администратор (Managed) | Управляет совместимостью и политиками без доступа к истории посещений сотрудников |

Не является критерием успеха: количество «красных значков», число сигнатур в каталоге, «100 % покрытие».

## 5. Модель доказательств (кратко)

Три независимые оси плюс coverage (ADR-001, ТЗ I §4.1):

- **Наблюдение** — что доступно инструменту (`evidenceSource`, `integrity`, `count`, `countQuality`, `phase`).
- **Интерпретация** — какая гипотеза объясняет последовательность (`interpretation`, `interpretationConfidence`).
- **Атрибуция** — какой скрипт/frame/host/продукт можно связать с фактом (`attributionConfidence`, `vendorConfidence`).
- **Coverage** — почему отсутствие событий может быть неинформативным (`coverageState`, `coverageFlags`).

Сообщения из MAIN world имеют `integrity: page-controlled`: страница может их подделать. Это маршрутизация, а не аутентификация (REQ-004).

## 6. Каталог утверждений (claims catalog, E01-01)

Тип evidence: **observed** — утверждение прямо соответствует наблюдённому событию или собственному состоянию расширения; **inferred** — вывод движка интерпретации из сочетания наблюдений, всегда с `interpretationConfidence`; **catalog** — сведения из встроенного реестра/документации (описание продукта, известное ограничение), а не наблюдение на этой странице.

## 7. Coverage-состояния и обязательные экраны

`coverageState`: `active | partial | late-start | paused | unsupported | no-access | degraded` — всегда рядом с выводами (REQ-006). Обязательные состояния UI (ТЗ V §7): ещё нет разрешения; разрешение отозвано; страница открыта до активации; идёт наблюдение; ничего не наблюдалось в доступной области; известные слепые зоны; датчик отключён; лимит событий; пауза; контекст сменился; неподдерживаемая страница; несовместимая версия Chrome; настройки организации. Точные строки — `docs/ui-copy.md`.

## 8. Нефункциональные требования (бюджеты v1, ТЗ VI I1)

32 событий/batch, 16 KiB/batch, строки ≤512, 20 batch/s/document, 100/tab, 200/extension, bridge ring 512, flush 250–500 мс, ≤128 счётчиков/document/группа, ≤256 находок и ≤128 hosts/document, 100 KiB/report, 4 MiB session total, TTL неактивного документа 10 мин, out-of-order карантин 2 с/128 записей, Math ≤8 stack samples/2 с/realm. Превышение → `degraded` с `coverageFlags`, не зависание. Целевые показатели производительности (popup p95 ≤300 мс, находка p95 ≤1 с, main thread p95 ≤5 % и ≤50 мс за первые 5 с) — предлагаемые цели до измерений (ADR-011).

Chrome floor 119 (API); фактический `minimum_chrome_version` — из `browser-support.json` (ADR-002). `incognito: not_allowed` в v1.

## 9. Критерии готовности

**Срез 1 (сквозной прототип):** один canvas-сенсор (DET-001…DET-003, DET-004 только для realm Window) → недоверенный ISOLATED bridge → SW reducer по `documentId` → engine → `storage.session` → popup с coverage. Проверки: controlled positive canvas fixture и обычный редактор (negative), tainted canvas, исходное исключение, повторная установка, malformed/flood bridge, BFCache, отзыв разрешения. Контрольная точка: после среза 1 не добавлять детекторы, пока не пройдут E02/E04/E05/E06 (внутренний отчёт).

**Definition of Ready к публичному запуску (ТЗ V §12):** нет открытых критических дефектов совместимости/утечки; Local работает офлайн; ключевые техники имеют положительные и отрицательные fixtures; все каталожные заявления подтверждены; UI показывает неизвестное и неполное наблюдение; privacy policy отражает действительную обработку; rollback отрепетирован; назначены владельцы.

Статус приёмки среза 1 (аудит 2026-09-12, F006/F007/F077): контрольная точка **не пройдена**. Отзыв разрешения пропущен (`test.fixme`), SW kill до save и после save/до ACK не проверен на Chrome (E02-03), редактор даёт расхождение с negative control (E07-01 #2), измерение `measureText` ×10⁶ отсутствует (E07-01 #11). Успешный exit тестового набора не закрывает эти требования; фактические границы — внутренний отчёт §4 и `docs/coverage/sw-restart.md`.

## Ограничение доказательств интеграции 2026-09-12

CLM-S2 проверен на контролируемых fixtures: наблюдение включено на старте, readiness markers подтверждают захват UI/SW console, wire проверяется до прикладной валидации, extension-attributed egress не обнаружен. Успешный test:privacy не доказывает отсутствие произвольных hostname identifiers: live hostname canaries с optional grants и reviewed offline PSL остаются открытыми (F038/F181). Branded Chrome support не заявлен. Изменённые публичные строки остаются предметом owner review ADR-001/003/007.
