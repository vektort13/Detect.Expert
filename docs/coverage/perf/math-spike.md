# P09 — стоимость обёрток Math

Связи: внутренний отчёт, задача 8; E02-02; ADR-011/ADR-012; ТЗ III §3.2–3.5, VI I4; REQ-002/005/011/015.

## Результат: no-go

Замер 2026-09-13T08:15:31.538Z: Windows 10.0.26200 x64, AMD Ryzen 9 7950X (32 логических CPU), 127,13 GiB RAM, Node v25.2.1, Playwright 1.63.0. CDP: **Chrome/153.0.8010.12**, V8 15.3.76.4; UA сообщает HeadlessChrome/153.0.0.0. Это один мощный стенд, не подтверждение поддержки branded Chrome. Другие проверки репозитория во время perf-прогона не запускались.

Анимация во всех режимах дала 601 кадр, p95 межкадрового интервала 8,4 мс. Медиана времени вычислений на кадр: baseline 0,0118 мс, fast 0,0150 мс, naive 0,9631 мс. Это фиксированная небольшая rAF-нагрузка; сохранение числа кадров не доказывает отсутствие влияния на более тяжёлый рендер.

**Решение: no-go для текущей постоянной Math-обёртки и начала E09 по этому прототипу.** На заранее выбранном горячем сценарии fast даёт +53,33 % медианы при предложенном пределе +5 %. Даже без stack и доставки данных цель не достигнута. Naive увеличивает время миллиона sin примерно в 126 раз относительно baseline и в 82 раза относительно fast, подтверждая неприемлемость stack на каждый вызов на этом стенде. Это данные для решения, не доказательство невозможности любой будущей реализации Math.

## Методика

`pnpm test:perf:math` запускает Chromium 153 headless (`channel: chromium`) без расширения. На каждый из пяти сценариев приходятся пять измерений каждого режима: baseline, fast, naive — всего 75. Каждый образец получает новый browser context/realm; профиль Chromium находится во временном каталоге ОС. Браузер один, измерения последовательные, порядок режимов циклически меняется. Перед измерением выполняются 1000 разогревающих итераций той же функции; для rAF — одно ядро из 256 пар sin/cos. После разогрева счётчики сбрасываются. Разогрев не доказывает стабилизацию JIT; распределение пяти прогонов сохранено полностью.

Медиана и nearest-rank p95 считаются по пяти прогонам; **p95 при n=5 — максимум**, а не надёжная оценка хвоста распределения. Overhead — разность соответствующих статистик, в миллисекундах и процентах к baseline. В JSON числа не округлены, в таблице округлены для чтения. Сценарий `single` заранее выбран горячим критерием: миллион sin. Предложенный порог ≤5 % медианы не является установленным фактом или гарантией продукта. Превышение даёт `no-go`, но не ошибку команды: задача команды — получить валидные измерения. Ошибка браузерной версии, нагрузки, счётчиков, маски, synthetic checksum или деградация наблюдателя завершают команду ненулевым кодом.

`families` выполняет по 100 000 вызовов sin, asin, sinh, asinh, exp, log, pow, sqrt (восемь семейств). `calculator` — 100 000 итераций пяти функций со строковыми операндами, coercion выполняет исходный Math. `physics` — 100 000 шагов обновления частиц (32 частицы по очереди), синусоидальная сила и линейное сопротивление. `animation` — 256 пар sin/cos в каждом rAF не менее пяти секунд. Для неё отдельно записаны число кадров, вычислительное время, время на кадр и интервалы кадров. Фиксированная длительность rAF сама по себе не показывает стоимость обёртки; короткие вычисления дополнительно чувствительны к дискретности `performance.now()`.

## Границы прототипа и рекомендация ADR-012

Обёртка находится только в `tests/perf/math/proto-wrap.js`. Включённость, reentrancy guard, насыщение до 2147483647 и маска используют заранее выделенные счётчики с числовыми кодами. Fast observer не создаёт явных объектов/массивов, не читает stack/часы, не отправляет сообщения. Для точной передачи аргументов применяется `Reflect.apply` с `arguments`: внутренние аллокации V8 и GC/heap growth не профилировались, обещания нулевых engine allocations нет. Naive-контроль читает `Error().stack` на каждом наблюдаемом вызове и сразу отбрасывает; в evidence остаётся только число чтений.

Прототип не сохраняет аргументы и результаты Math. Synthetic checksum создаёт сама fixture из собственных чисел, чтобы обнаружить изменение вычислений; это не данные сенсора. Вложенные Math-вызовы при coercion выполняются, но guard подавляет вложенное наблюдение: для такого случая счётчик даёт нижнюю границу. Повторная установка не идемпотентна; стенд устанавливает прототип ровно один раз в новом realm. Это не production-сенсор и не проверка готовности его lifecycle.

Для ADR-012 сохранить верхнюю границу **8 stack samples / 2 s / realm** и окна **250 ms / 2 s**. Эти параметры — бюджет и предмет следующего измерения, а не доказанная оптимальность. Стек на каждый вызов исключить. Если даже счётчик превышает бюджет, уменьшение числа stack samples не устраняет базовую стоимость: до E09 нужен отдельный оптимизированный или ограниченный вариант с повторным go/no-go; деактивация должна быть явной для coverage. В этом spike окна, sampled attribution, таймеры, bridge, storage и classifier не реализованы и их стоимость не измерена. ADR-011/012 остаются Proposed.

**второй класс оборудования не измерен**. Нет результата на слабом/среднем втором устройстве, доверительных интервалов, CPU/памяти за длительную сессию, branded Chrome acceptance, worker/WASM покрытия или качества классификации. Калькулятор и физика — обычные отрицательные нагрузки, но отсутствие classifier не позволяет заявить пройденный false-positive gate E09. Никакие thresholds/holdout/production flags не менялись.
