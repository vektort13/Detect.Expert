# ADR-013. Enterprise policy, CSP и auth

Статус: **Proposed**. Владелец: manifest/permissions + security (TBD). Реализация — E18 (Managed local), E19 (Connected).

## Контекст

AUD-28: нет корпоративного разделения данных. `chrome.storage.managed` + `storage.managed_schema` (верхний уровень `object`, `properties`, без верхнеуровневого `additionalProperties`); применение политик — задача расширения. Managed connected требует иной CSP и permissions; `ServiceOrigin` не должен открывать произвольный `https:`. Принудительная установка — не раскрытие обработки.

## Решение (предлагаемое)

1. Минимальный каталог политик (ТЗ V §4): `ObservationEnabled` (разрешение, не активация), `ObservationScope` (`user_permissions | allowed_sites`), `AllowedSitePatterns`, `ExcludedSitePatterns` (приоритет исключения), `DisabledSensorIds` (только локальный реестр), `RemoteRuleUpdatesEnabled=false`, `PinnedRulePackVersion`, `FleetHealthEnabled=false`, `ReportUploadMode=disabled|manual`, `ExportMode=redacted`, `LocalRetentionHours=24` (в безопасных пределах), `TenantId`, `ServiceOrigin`.
2. Приоритет: неотменяемые границы продукта и реальные browser permissions → ограничения организации → более строгий пользовательский выбор → безопасные defaults. Политика никогда не расширяет выданные Chrome разрешения и не включает несуществующий browsing upload.
3. Некорректная политика не стирает последнюю корректную; rejected keys — в диагностику; реакция на `storage.onChanged` без перезапуска где возможно; для перерегистрации скриптов/очистки хуков — требование reload в UI.
4. Профили сборки: Local/Managed local — `connect-src 'none'`, встроенный каталог, без OAuth. Managed connected — отдельный проверяемый manifest/CSP профиль с точными HTTPS origins control plane/IdP; `ServiceOrigin` выбирает только адрес из списка сборки. `chrome.identity.launchWebAuthFlow` — отдельный auth ADR и permission `identity`; в локальный пакет не добавляется.
5. Auth (Connected): device enrollment и пользовательский OIDC/SSO разделены; одноразовый enrollment-токен, ограниченный tenant и сроком; короткие access tokens с rotation/revocation; серверная проверка audience/issuer; credentials только в SW, никогда в MAIN/ISOLATED/диагностике; сервер не использует клиентский `tenantId` как основание доступа. Секреты в managed storage не хранятся.
6. UI: «Часть настроек задана вашей организацией», факт управления, получатель и состав передачи видны пользователю; `chrome://policy` — источник проверки для администратора. Admin guide содержит JSON Schema, пример deployment, приоритеты, словарь причин отклонения, процедуру удаления устройства.

## Последствия

- Managed local можно выпускать без backend (E19 опционален).
- Доставка — CWS и стандартные настройки организации; private-публикация внешним организациям — через обычный review; self-hosting не универсален.

## Приёмка

Профили сборки: production Local-пакет не содержит `identity`, внешних origins в CSP и enrollment-кода; невозможность скрытого endpoint (build scan + permissions diff); тесты rollout/отключения/отзыва доступа; администратор не может включить upload, которого нет в схеме; некорректная политика → last-known-good + диагностика.
