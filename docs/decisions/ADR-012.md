# ADR-012. Math: окна, семплы и интерпретация

Статус: **Proposed**. Владелец: `packages/sensors/math` + исследователь детекции (TBD). Реализация — E09-01…E09-03 после E02-02 go/no-go.

## Контекст

AUD-14/15: поэлементные Math-хуки обещали дешёвую per-script агрегацию; упрощённая история libm подавалась как механизм ОС-идентификации. ECMA-262 задаёт implementation-approximated результаты; V8 `tanh` делегирует `std::tanh` — зависимость от сборки, не доказанная точность классификации ОС. Задача — показать паттерн обращения к численным особенностям, а не идентифицировать компьютер пользователя.

## Решение (предлагаемое)

1. Контракт данных на realm: два окна (250 мс и 2 с), bitmask вызванных функций, насыщаемые счётчики, ring ≤128 номеров функций с крупными временными bucket, ≤32 attribution slots. Значения — в версионированной конфигурации, не «научно доказанные пороги».
2. Не хранить и не передавать: аргументы, хэши аргументов, результаты, мантиссы, строковые представления, `argsSummary`. Допустим лишь краткоживущий boolean совпадения с allowlist-маркером, вычисленный без coercion и без выхода аргумента из обёртки; начальный релиз может обойтись без маркеров.
3. Fast path: `enabled? → reentrancy guard → счётчик++ → mask`; stack только на новом типе события в бюджете ≤8 samples/2 с/realm; после исчерпания — счётчики продолжаются, атрибуция `sample-budget-exceeded`.
4. State machine: `idle → numeric_activity → diverse_burst → candidate → calibrated_match`; отдельно `budget_exceeded`, `coverage_degraded`; наружу — изменение состояния или ограниченный агрегат (≤1 за 500 мс), не поток вызовов.
5. Правила: одиночные/однотипные вызовы → только счётчик; разнообразие семейств в коротком окне (экспериментально ≥6 различных функций) → candidate, но не единственный production-критерий; дополнительные признаки — порядок как у проверенного collector, allowlist-маркеры, близкая по времени графика/аудио/локаль; `high` только для валидированного шаблона; смешанные скрипты/потери/исчерпанный бюджет → ниже или «недостаточно данных»; численное соответствие платформе не вычисляется.
6. Атрибуция: базовый агрегат — документ/realm; samples хранятся отдельно; противоречивые samples → неоднозначно на уровне документа; нельзя приписать все вызовы окна одному скрипту.
7. UI: «Серия численных проверок похожа на известный шаблон», не «ваш процессор определён».
8. Сигнатуры последовательностей — собственный декларативный формат в коде с `ruleVersion`, источником, fixture ID; формула `sinhPf` из исходника не переносится как нормативная.

## Последствия

- Math-модуль выпускается ограниченным режимом, если overhead (E02-02) выше бюджета.
- Positive fixtures: зафиксированные open collectors (FingerprintJS с commit/лицензией, CreepJS из канонического репозитория) и собственные сценарии; negatives: графики, карты, калькулятор, физика, DSP, ML, benchmark.

## Приёмка

Benchmarks на 10⁶ вызовов без stack/IPC/storage на вызов (измеренный overhead в отчёте); negative math workloads не дают candidate; positive sequence обнаружена; malformed batch/повторная установка; пороги не меняются ради теста (ADR-010).
