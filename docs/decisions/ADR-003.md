# ADR-003. Модель разрешений и onboarding

Статус: **Accepted** (2026-09-12). Владелец: manifest/permissions (один владелец; изменения только через новую версию ADR).

Редакция **v2** (2026-09-12, F088/F167): сверка документа с существующим manifest и `SCOPE_MODES`; на review владельца manifest/permissions. Статус Accepted относится к исходному решению; review v2 ещё не зафиксировано. Новые разрешения или статические scripts этой редакцией не вводятся.

## Контекст

AUD-07: `<all_urls>` выбран без режима доступа. `activeTab` даёт временный доступ к origin основной страницы после действия пользователя; `webRequest` для subresource требует разрешений и на target, и на initiator. Unregister не удаляет уже внедрённый скрипт. CWS требует минимальные permissions и раскрытие обработки. После установки наблюдение должно быть выключено.

## Решение

1. **Три уровня наблюдения** плюс `off` (по умолчанию после установки):

| Режим | Разрешения и запуск | Что честно обещает UI |
| --- | --- | --- |
| `active-tab` — «Проверять с этого момента» | Chrome permission `activeTab` + `scripting`; поздняя инъекция (`scripting.executeScript`, MAIN + ISOLATED, `documentIds: [documentId]`) только в захваченный top document текущей вкладки после клика | Наблюдения после включения; `late-start`; ранние вызовы могли быть пропущены |
| `site` — «Всегда на этом сайте» | Optional host permission для origin (`permissions.request`); `scripting.registerContentScripts` с `id: detector-isolated-v1` (ISOLATED, `bridge.js`) и `detector-main-v1` (MAIN, `hook.early.js`), `runAt: document_start`, `allFrames: true`, `matchOriginAsFallback: true`, `persistAcrossSessions: true`, matches = разрешённые origin patterns | Ранние вызовы при следующей загрузке; сторонняя сеть видна частично (`network-limited`) |
| `all-sites` — «Наблюдать на всех сайтах» | Явно выданный `optional_host_permissions: ["http://*/*", "https://*/*"]`; matches `http://*/*`, `https://*/*`; сетевой наблюдатель | Наиболее широкий доступ без обещания workers/DNS/серверной логики |

2. Manifest (профиль `local`): `permissions: ["activeTab", "scripting", "storage", "webRequest", "webNavigation", "sidePanel"]`; `optional_host_permissions` как выше; **нет статических `content_scripts`**; `incognito: not_allowed`; `minimum_chrome_version` из `browser-support.json` (floor 119). Исключены: `tabs`, `cookies`, `debugger`, `history`, `nativeMessaging`, `declarativeNetRequest`, `unlimitedStorage`, `identity`.
3. **Test-профиль** (`apps/extension/manifest.ts` profile `test`) отличается от `local` только суффиксом имени ` (test)` и статическим `host_permissions: ["http://127.0.0.1/*"]` для loopback-стенда. В обоих профилях **нет `content_scripts` в manifest**: регистрация динамическая через `scripting.registerContentScripts`; поздняя инъекция — через `executeScript`. Test использует существующий статический грант при стартовой регистрации. `tests/extension/smoke.spec.ts` проверяет `expect(manifest.content_scripts).toBeUndefined()`; `pnpm release:verify` отклоняет loopback-grant и статические scripts в production-пакете.
4. Существующие разрешения проверяются (`permissions.contains`) до запроса; повторный запрос без необходимости не показывается. Обнаружение нового домена **не** расширяет разрешения автоматически — UI показывает ограничение.
5. **Отзыв** (`permissions.onRemoved`, изменение политики, `ui-set-scope`): `unregisterContentScripts` для scope → SW прекращает приём батчей scope (`Ack.paused`/`bridge-stop`) → bridge ставит локальный флаг паузы, сенсор прекращает наблюдение → best-effort восстановление оригиналов только при проверке владения дескриптором (ADR-006) → данные scope удаляются по политике → UI: `no-access` + `revoked`, «перезагрузите страницу для полного удаления датчиков».
6. Разделение «разрешение документа» и «origin файла скрипта»: сторонний `<script src>` в разрешённом документе попадает в MAIN-хуки; сетевой канал `webRequest` к его host — только при разрешении на target и initiator. UI показывает script origin и document origin раздельно.
7. Onboarding до начала наблюдения: объяснение трёх уровней, «расширение может быть замечено сайтом», «не отправляет результаты анализа», ссылка на privacy policy.

## Последствия

Канонические значения `scopeMode`: `off`, `active-tab`, `site`, `all-sites` (`packages/contracts/src/enums.ts`). `activeTab` в колонке разрешений — имя Chrome permission. Фактическая запись предпочтений — `scope: { v: 1, scopeMode, hosts }`, см. `docs/data-inventory.md` §4.

- Первый открытый документ в режиме `site`/`all-sites` до перезагрузки — `late-start`; кнопка «Перезагрузить для анализа с начала».
- Managed local (ADR-013) может только сужать scope (`AllowedSitePatterns`, `ExcludedSitePatterns`), никогда не расширяет выданные Chrome разрешения.
- `ws:`/`wss:` handshake учитывается только после подтверждения permission matrix на поддерживаемой версии Chrome (E10-01).
- Политика приложения: grant active-tab истекает при любой cross-document навигации, включая same-origin (см. уточнение ниже).

## Проверено в браузере

2026-09-13, P05/F006/E06-02/REQ-013, расширение 0.1.0, профиль `test-optional`, Windows x64, Playwright 1.63.0, headless Chromium **153.0.8010.12** (`browser.version()` и CDP `product`; сокращённый userAgent — 153.0.0.0, bundled build 1243). Целевая матрица `tests/extension/permissions/matrix.spec.ts`: **7 passed, 1 fixme**, последовательно, отдельный временный профиль ОС для каждого теста. Это свидетельство стенда, не подтверждение branded Chrome/всех поддерживаемых версий.

Редакция P05 добавляет `test-optional`: то же optional host allowlist и CSP, что у `local`; отсутствуют статические `host_permissions` и стартовый test-bootstrap. Имя содержит `(test-optional)`. Скрипты `build:test-optional` и `test:extension` собирают этот профиль. UI-параметр `tabId` и DevTools-only `__p05.reconcilePermissions` существуют только в тестовых сборках; в `local` удаляются при сборке. Хук сначала требует реальный `permissions.contains`, затем вызывает обычную обработку изменения разрешений. Он не выдаёт разрешения, не меняет scope и не добавляет wire API. `release:verify` собирает только `local`, отклоняет тестовые имена/статические grants/остатки `__p05`; шесть script-регрессий проверяют manifest и границы сборки для трёх профилей. Новых permissions/зависимостей/CSP нет; изменение manifest ограничено разрешённым карточкой тестовым профилем.

- Нет гранта: нет регистрации и обёрток; вызовы canvas и поддельный MAIN batch не создают наблюдений; popup показывает отсутствие доступа вместе с выключенным scope.
- `active-tab`: CDP `Extensions.triggerAction` на browser-сессии и target типа `tab` вызывает настоящее действие toolbar, затем Playwright кликает кнопку реального popup, открытого страницей расширения. Грант optional отсутствует, инъекция имеет `late-start`; другая вкладка и новый документ после same-origin reload не получают доступ. Для этой автоматизации только harness использует `--enable-unsafe-extension-debugging`; это не разрешение расширения.
- `site`: после выдачи реального optional-гранта первые `fillText` при загрузке наблюдаются; `neighbour.test`, локально направленный в loopback, остаётся `no-access`. Разные порты одного hostname не использовались как отрицательный permission-case: Chrome match patterns не разделяют их.
- `all-sites`: первые вызовы наблюдаются на обоих hostname стенда; это не проверка всей внешней сети/HTTPS/WSS.
- Настоящий `permissions.remove` из SW: `contains=false`, регистрация пуста, idle-мост получает `bridge-stop(revoked)`, отчёт очищен, popup содержит `no-access`, `revoked` и объяснение reload. Чужая обёртка над нашей сохраняет identity. После reload `toDataURL`, `toBlob`, `getImageData`, `measureText` совпадают с чистым Chromium по intrinsic `Function.prototype.toString.call`, обычному `toString`, `name`, `length`, configurable/writable/enumerable. Между realm нельзя сравнить исходные function-объекты по `===`; это не обещание такой identity.
- Сужение `all-sites → site → active-tab → off` при сохранённом широком гранте: реальные сообщения из ISOLATED исключённых документов получают `Ack(lastCommittedBatchSeq:0, paused:true, protocolOk:true, stopReason:revoked)`. Соседняя вкладка того же host также исключается в active-tab. Разрешённый документ продолжает накапливать данные до своего исключения.

Первичный `permissions.request` после активированного Options-клика остаётся в нативном диалоге. Единственный `fixme` требует независимого свидетельства из `chrome://accessibility`: `ExtensionInstallDialogView`, `ExtensionPermissionsView`, текст запроса дополнительных разрешений и конкретный host. Произвольное зависание Promise не считается причиной skip. Дерево приложено к Playwright-результату. Резервный путь: API настроек самого Chromium `developerPrivate.addHostPermission` для обеих схем, затем **реальный** `permissions.request` через кнопку Options, `permissions.contains` и тестовый хук обычной reconciliation. Нет подмены API, редактирования Preferences или статического гранта. [Реализация Chromium](https://raw.githubusercontent.com/chromium/chromium/main/extensions/browser/api/permissions/permissions_api.cc) объясняет повторный запрос ранее одобренного runtime host без нового предупреждения. Внутренний API стенда может измениться: его ошибка должна завершать тест failure, а не fake/skip.

Приём первого нативного prompt человеком в headful Chrome остаётся непроверенным. Немедленный stop добавлен в существующий SW→ISOLATED control (ADR-004, запись 2026-09-13); старому уже внедрённому bridge до обновления/reload нельзя обещать поддержку новой команды. Сужение в `scope.ts` не потребовало изменения: browser-регрессия подтверждает существующую проверку F002. Полные команды, ограничения общей рабочей копии и независимый review: внутренний отчёт.

## Приёмка

Тесты (E02-01, E06-02, `tests/extension/permissions`): no access → `no-access`; `active-tab` → `late-start`, наблюдения после клика; `site` → `active` при следующей загрузке, cross-origin iframe без разрешения → `frames-inaccessible`; `all-sites` → `active` во всех HTTP(S) frames стенда; revoke во время наблюдения → новых батчей нет, `revoked`, reload убирает обёртки; third-party script в top frame наблюдается, запрос к его host — по матрице target/initiator. Permissions diff production-пакета совпадает с этим ADR.

## Уточнение интеграции 2026-09-12 (F083/F137, REQ-013)

В реализации active-tab разрешён только захваченный top document: обе инъекции адресуются через documentIds: [documentId]. Любая cross-document навигация, включая same-origin, прекращает это разрешение; SPA с тем же documentId сохраняет его. Это консервативная политика приложения, не утверждение о сроке Chrome activeTab. Поздний старт назначается только той же текущей идентичности, не наблюдавшей сенсор до инъекции. Регистрация скрипта сама по себе не доказывает инъекцию в документ.

Активация меняет scope после успешной инъекции; ошибка сохраняет предыдущий scope и grant. site/all-sites регистрируют hook.early.js в document_start; ручная инъекция использует hook.main.js без гарантии раннего захвата. Статический тестовый bootstrap включён только compile-time test profile. Permissions/CSP не расширены. Idle-worker TTL alarm не добавлен: нужен отдельный review разрешения alarms и планировщика (F171).

Пройденный headless Chromium late-start/revoke стенд использует статические grants; toolbar activeTab и настоящий optional-grant revoke остаются отдельной приёмкой владельца.

## Предложение: alarms

Статус: **Proposed**, 2026-09-13, P02/F171. Разрешение `alarms` не добавлено, manifest/CSP не изменены.

Event-driven TTL по ADR-005 обеспечивает удаление на следующем событии расширения после истечения 10 минут с амортизацией 30 с. `setInterval` остановленного MV3 service worker не выполняется. Поэтому строгое требование ТЗ об удалении ровно через 10 минут без внешнего события текущими разрешениями невыполнимо. Предлагается отдельный review владельца permissions: возможность будить SW через `chrome.alarms`, восстановление расписания после старта и измерение фактической задержки. Даже такой механизм потребует явно описать задержки браузера/сна ОС и не обещать точный wall-clock deadline без подтверждения. До решения используется раскрытая пользователю событийная деградация; P02 не выдаёт её за точный таймер.
