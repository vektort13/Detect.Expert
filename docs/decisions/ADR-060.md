# ADR-060 — WebRTC Custom и отдельная сетевая политика

Статус: WebExtensions scope реализован, независимо проверен и прошёл Chrome/Firefox native gates. Итоговый отчёт. DTLS identity на всю browser session остаётся открытым требованием; реализована отдельная опция per-connection. Продолжает ADR-048/049, задача E22-08. Владелец выбрал оба режима отдельно, затем поручил реализовать рандомизацию всех устройств, обновляемую при запуске браузера и стабильную внутри сессии. Последующим уточнением сертификаты ограничены только DTLS WebRTC; HTTPS/TLS вне задачи.

## Два независимых управления

Существующий API `webrtc` сохраняет ID и позицию; Custom получает типизированный профиль: `addresses` (null либо host/stun/turn как буквальные IPv4/IPv6), `iceTransportPolicy` (preserve/relay), `randomizeDevices`, `freshCertificates`, `deviceLifetime` (session/site только для идентификаторов устройств). Формат конфигурации 2, каталог 3; строгая миграция прежних format1/catalog1 и format1/catalog2 сохраняет режимы, selected, библиотеки и сайты. Новая глобальная `webrtcNetworkPolicy` по умолчанию system. Существующие 142 ID и порядок не меняются.

`privacy.network.webRTCIPHandlingPolicy` управляет нативной сетевой политикой всего браузера. В обоих manifest добавляется только **optional** permission `privacy`; пользователь отдельно предоставляет его кнопкой доверенного UI. Доступные значения — system (снять только своё управление), default_public_interface_only и disable_non_proxied_udp. Проверяются permission, поддержка, levelOfControl и фактическое значение после set/clear. Другой владелец не перезаписывается. При system снимается и наш слой, скрытый более новым расширением: clear удаляет только собственное значение и не меняет значение того расширения. Иначе старый наш policy мог бы воскреснуть после удаления более нового владельца. Ошибка clear/rejection/Firefox false сохраняется в статусе до подтверждённого освобождения. Политика отдельная от общего API master и сайта, включается только явным выбором пользователя после согласия. Нет новых host permissions, CSP, удалённых запросов или внешнего управления.

Произвольный Custom IP меняет покрываемые JS metadata, но не исходный адрес пакета STUN и не адрес настоящего выделенного TURN relay. Реальный выходной IP определяется работающим маршрутом/VPN/прокси/TURN; расширение не создаёт их. Relay использует настроенные сайтом TURN-серверы; при их отсутствии native ICE может не установить соединение. В этой реализации не добавляются TURN credentials или внешний relay service.

## Ранняя установка и согласованность

RTC installer включается в прежнюю закрытую native document_start регистрацию и наследование realm, без публичного stop/restore и команд страницы. Custom не применяется к недоступному API. Адреса санитизируются согласованно на покрываемых candidate/SDP/stats/transport/error поверхностях. Обратная подстановка для штатных локальных вызовов остаётся закрытой в WeakMap/локальной памяти. Подмена адреса, переданного внешнему удалённому peer, может нарушить ICE; Custom metadata не объявляется сетевым туннелем.

Рандомизация устройств относится к идентификаторам реально доступных устройств, с обратным сопоставлением при выборе. Не создаёт микрофоны, камеры или разрешения. Источники псевдонимов — собственные случайные salts: session в storage.session, site в storage.local. В конфигурацию/экспорт не попадают нативные идентификаторы, устройства или salts. Псевдонимы разделяются по origin. При холодном запуске обновление persistent userScripts с новым session seed асинхронно; до завершения ранее зарегистрированный код может сохранять прежние случайные псевдонимы. Это не раскрытие исходного deviceId, но мгновенная ротация до самого первого inline-скрипта не заявляется.

Fresh certificates означает новую настоящую нативную DTLS identity для каждого PeerConnection, без повторного использования переданных страницей сертификатов. SDP fingerprints, DTLS и stats должны соответствовать тому же настоящему сертификату. Строки fingerprints не рандомизируются отдельно, сертификаты TLS/HTTPS и хранилище доверия ОС не изменяются. Закрытые ключи не создаются расширением, не читаются и не экспортируются.

Требование владельца о стабильности случайных значений в пределах browser session выполнено для идентификаторов устройств. Для DTLS оно остаётся невыполненным: отдельная опция freshCertificates явно означает новый сертификат на соединение. Native generateCertificate асинхронен, сертификат нужен синхронному конструктору заранее и привязан к origin создателя; один extension-origin certificate нельзя использовать на произвольных сайтах. Перенос opaque handle не снимает origin restriction. В текущем WebExtensions scope нет гарантии единого настоящего session certificate до первого вызова сайта во всех новых документах. Не заменять это обещанием поддельного fingerprint или скрытой виртуализацией PeerConnection. [WebRTC certificate management](https://w3c.github.io/webrtc-pc/#rtccertificate-interface).

Включение/изменение относится к новым документам по ADR-049. Сохранённые ссылки/результаты и уже установленные соединения нельзя отозвать задним числом. Workers и иные непокрытые области не объявляются закрытыми.

## Проверки и источники

Независимые review manifest/схем/семантики API выполнены. Строгие миграции, отказ storage/permission/control, холодный запуск и владение нативной настройкой покрыты; Chrome153/155 и Firefox138 fixtures с контролируемой собственной сетью прошли. Общий unit gate — 3429 PASS; обязательный release:verify — PASS. Точный scope, сохранённые неуспешные попытки, native assertions и hashes приведены в итоговом отчёте; это не подтверждение произвольного оборудования и всех версий браузеров.

## Дополнение 2026-11-06 (раунд 5): `proxy_only` для Firefox

Дополнение 2026-11-06 (раунд 5). Для Firefox выбор расширен значением `proxy_only` (формат 9 / каталог 10; форматы 2–8 знают три значения). Оно есть только в
`privacy.network.webRTCIPHandlingPolicy` Firefox (Firefox 138.0.4: схема `privacy.json`, значение `media.peerconnection.ice.proxy_only`) и строже `disable_non_proxied_udp`:
весь трафик WebRTC идёт только через прокси, поэтому без прокси, передающего UDP, звонки не работают (измерено: Firefox 138.0.4 без прокси — 0 ICE-кандидатов против 4 на базовой
линии, `iceGatheringState` остаётся `new`). Chrome 153.0.8010.12 и 156.0.8078.80 отклоняют значение своим API («Invalid invocation»), поэтому Chrome его не предлагает и не применяет.
Значение выбирается только в сборке Firefox (страницы `moz-extension://`) и считается применённым только после чтения через нативный API: точное `proxy_only` и владение
`controlled_by_this_extension` (ADR-060, ADR-072 без изменений). В Chrome значение скрыто; сохранённый выбор (импорт, правка хранилища) показывается заблокированным со статусом
«Недоступно в этом браузере», нативная настройка не читается на запись ни одним вызовом (`set` и `clear` не вызываются, пока нет собственного слоя), а применение — сохранение с
включённым мастером Antidetect — отклоняется фиксированным кодом `webrtc-policy-unsupported`. При активном модуле «Прокси» (ADR-070) действует более строгое из двух значений:
`proxy_only` не ослабляется до `disable_non_proxied_udp`, а при выключении выбора остаётся требование модуля «Прокси». Новых permissions, CSP, сети, каналов сообщений и ключей хранилища нет.
Не проверено: Firefox 128 (нижняя граница `strict_min_version`) — значение подтверждено в схеме Firefox 138.0.4.
