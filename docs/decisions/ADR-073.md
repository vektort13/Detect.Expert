# ADR-073 — барьер сброса наблюдения и долговечная граница очистки

2026-10-30. Исправление CORE-01/02 по прямому решению владельца продукта, уточнение ADR-072. Задача E22-28. Реализация завершена, независимые source reviews приняты; фактические проверки и ограничения зафиксированы в итоговом отчёте и coverage.

## Причина

SW baseline не знает о ещё не переданных cumulative counters. Вычитание последнего принятого максимума возвращает старую историю как для известного ключа, так и для впервые доставленного после очистки ключа. Поэтому baseline-only не является достаточным исправлением.

## Протокол и границы доверия

SW вызывает новый `bridge-control/reset` с bounded `resetId` через native `tabs.sendMessage` по точному `documentId/frameId`. ISOLATED сохраняет прежнюю проверку `MessageSender`: собственный extension ID/origin и отсутствие `sender.tab`. Эта проверка допускает доверенные собственные extension contexts; штатный инициатор — service worker. MAIN не может инициировать привилегированную очистку.

ISOLATED останавливает предыдущую delivery epoch, затем отправляет отдельный `bridge-reset` известным MAIN boot. MAIN очищает counters/dirty/association history, оставляет установленные hooks и их семантику, меняет `sensorBootId` и отвечает `sensor-reset {resetId,nextSensorBootId}`. MAIN-сообщения по-прежнему page-controlled; IDs обозначают маршрутизацию, не аутентификацию. Один повтор resetId идемпотентен. Callback/error/gap и все ожидания ограничены.

После ответов всех известных boot ISOLATED использует свежий `bridgeSessionId`, пустой ring и fresh boot allowlist (не более четырёх). Старые in-flight ACK не меняют новое состояние; старые сообщения/boot/session не переносятся в новую epoch. Нативный ответ SW — `bridge-reset-ack` с тем же resetId и только routing IDs. Отсутствующий или не подтвердивший reset активный актор не считается успешно сброшенным.

## Долговечность

ClearSession резервирует очереди всех затронутых документов. Producer reset выполняется до logical commit. Авторитетная граница очистки — **один** metadata-only item `clear-epochs:v1` с bounded списком `{documentKey,bridgeSessionId,sensorBootIds,at,reportRevision,paused?}`. На недокументированную атомарность записи нескольких storage-ключей решение не опирается. Точный bounded размер JSON журнала/ключа в UTF-8 входит в прежний общий бюджет 4MiB и резервируется до записи authority, пока старый payload ещё существует.

Loader применяет committed fence до выдачи history/inspectors: старый doc snapshot с несовпадающим `meta.clearEpoch` не восстанавливается. Новые records сохраняют matching epoch. Fence хранит монотонный `reportRevision` floor, применяемый после restart; во время clear awaits промежуточные pre-clear projections скрыты. Пустой внутренний record отмечен `meta.cleared` и скрыт до нового наблюдения, кроме пустой paused projection с рабочим Resume; optional `paused` в fence сохраняет этот control state после restart. Counters/findings/hosts и прежний report watermark отсутствуют. Cumulative baseline со старыми ключами не удерживается, поэтому cap128 не обходится повторными clear и saturation старого boot не блокирует новый отсчёт.

Payload cleanup идёт после authoritative commit. Ошибка cleanup не подавляется: вызывающий получает ошибку, committed fence остаётся и предотвращает resurrection, cleanup повторяется при восстановлении. Сбой до authoritative commit сохраняет прежние ACKed reports; успешно сброшенные акторы имеют новые boot IDs и могут продолжить прежнюю историю. Возможная потеря только volatile unACKed данных при abort должна давать явный gap. Успех не подтверждается при неизвестном исходе.

Fences ограничены прежним global document budget (1024). Payload удаляется по прежнему TTL; routing-only fence остаётся, пока открытая вкладка может вернуть BFCache документ, и удаляется после успешного удаления payload при закрытии вкладки. Inactive/revoked/no-access history допускает pending-reset-on-restore без ожидания недоступного актора. Старые epochs до завершения reset не принимаются. Если journal write после нового physical reset отказал при уже существующей fence, сбор остаётся degraded до явного Retry; прежние ACKed reports сохранены, ложного успеха и обещания прозрачного восстановления нет. Новых permissions, CSP, сети, DOM/value readers, detector thresholds и MAIN privileged commands нет.

## Приёмка

Нужны реальные и изолированные regressions: pending known/unseen key до clear, old buffered batches и поздний ACK, saturation, 128 old→new keys, первый новый вызов=1, повтор resetId, отказ reset/storage/cleanup, torn multi-key cleanup, SW restart, BFCache/native identity. Отдельный reviewer проверяет trust/nonce routing, sender checks, boundedness, authoritative commit, replay и сохранение семантики hooks. Оригинальные tests не ослабляются для зелёного результата.

Невозможность прочитать authority либо malformed journal при hydration запрещает ingress и persistence до успешного повторного чтения. Shared single-flight retry выполняется перед batch/UI mutation; browser events остаются bounded-buffered. Пустое состояние не считается доказательством отсутствия fence. Восстановление валидного authority повторно применяет fence до первого принятого payload. Нативные control/Ack readers читают только bounded own data descriptors, не выполняя accessors или input iterators.
